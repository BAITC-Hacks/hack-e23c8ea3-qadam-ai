## Демо

Сценарий рассчитан максимум на 5 минут. Все тексты ниже синтетические. Машиночитаемый вариант: [demo-inputs.json](demo-inputs.json) — ответы, карточки по этапам и два предложения команд.

Оценки **10 → 57 → 80** проверены отдельным расчётом по формуле `AGENTS.md`, для точных текстов карточек в JSON. Это ожидаемые оценки согласованного бэкенда, а не результат запуска приложения. В main `15b2ac3` формула фронтенда отличается, бэкенд ещё отсутствует. Перед защитой нужно сверить числа с реальным `rating.py` и прогнать интерфейс. Перефразирование моделью может изменить длину полей и оценку.

### 0:00–0:30. Слабый черновик

Роль: бизнес. Компания: **Демо-пекарня «Тёплый хлеб»**, `business-bakery`. Тема: **Общественное питание** (в текущем UI — HoReCa).

Вставить:

> У нас небольшая пекарня. Хотим меньше списывать непроданную выпечку в конце каждого рабочего дня.

Реплика: «У бизнеса пока только общая потребность. Система помогает уточнить задачу и показывает, каких сведений не хватает для начала работы».

В заглушке весь черновик попадает только в context: предварительно 10 баллов. Настоящий ИИ может отдельно извлечь need — тогда предварительная оценка будет иной.

### 0:30–1:40. Ответы на уточняющие вопросы

Вставлять по смыслу поля вопроса, а не по порядковому номеру: модель может менять порядок и формулировки.

| Поле / смысл вопроса | Подготовленный ответ |
|---|---|
| title — название | План выпечки для демо |
| data — доступные данные | Предоставим обезличенную таблицу продаж и списаний по видам выпечки за месяц. |
| expected_result — что сдаёт команда | Ожидаем таблицу с рекомендациями по количеству выпечки на следующий день. |
| success_criteria — как проверим | Сравним с ручным подсчётом. |
| need — что хотим изменить | Хотим сократить списания выпечки. |

Это пример набора из пяти вопросов, а не требование к точному порядку ответов модели. Если система спросила другое поле, используйте банк ответов `answer_bank` из JSON. Перед подтверждением проверьте карточку; для воспроизводимого этапа «Рабочая» приведите её к `stages.working` через редактор, сохранив только перечисленные выше поля и исходный context. Если модель уже получила больше сведений, не удаляйте их ради искусственного занижения рейтинга: покажите фактический результат.

У `stages.working` ожидается **57 баллов**: context 10 + need 5 + data 20 + expected_result 15 + success_criteria 7. Остальные поля пока пусты, название баллов не даёт.

Реплика: «Карточка уже позволяет понять результат и доступные материалы. Но критерий приёмки ещё расплывчатый, и нет формата связи с бизнесом».

### 1:40–2:40. Улучшение карточки

Через редактор дополнить и подтвердить следующие поля:

| Поле | Текст |
|---|---|
| need | Нужно сократить списания выпечки с помощью планирования выпуска на завтра. |
| success_criteria | На контрольных данных сумма списаний совпадает с ручным подсчётом в 100% строк. |
| contact | bakery-demo@example.com |
| interaction_format | Один видеозвонок по пятницам, обратная связь письмом в течение двух рабочих дней. |

Ожидается **80 баллов**, уровень «Готовая»: +5 за подробную потребность, +8 за измеримый критерий, +5 за контакт, +5 за взаимодействие. Критерий проверяет корректность расчёта; снижение реальных списаний ещё не обещано и не измерено.

Если система задаёт вопросы о пользователях и ограничениях, готовые ответы:

- users: «Рекомендациями будут пользоваться владелец пекарни и пекарь при планировании ежедневного выпуска.»
- constraints: «Прототип нужно подготовить за четырнадцать дней, используя только обезличенные таблицы бизнеса.»

Оба поля вместе доводят точную карточку из JSON до **100 баллов**. Это необязательное продолжение, чтобы не затянуть демо.

### 2:40–3:10. Публикация

Подтвердить карточку вручную, затем опубликовать. Найти новую задачу **«План выпечки для демо»** в общем каталоге. Не путать с заранее загруженной **«План выпечки на завтра»** (`task-bakery`).

Реплика: «Полнота повышает позицию задачи. При этом задача с низким рейтингом тоже видна всем и принимает отклики».

Для набора из seed при 80 баллах новая задача идёт ниже задачи на 100 и выше старой задачи на 80, если updated_at новой карточки позднее. Фильтры на время демонстрации отключить.

### 3:10–4:15. Две команды предлагают решения

Сначала выбрать **Демо-команда Data Qadam** (`team-data`), открыть новую задачу и отправить:

- Идея: «Построим таблицу рекомендаций на основе продаж и списаний по дням.»
- План: «Проверим структуру данных, подготовим базовые расчёты, сравним результаты с ручным подсчётом.»
- Срок: «Прототип через 7 дней после получения данных.»
- Ссылка: `https://example.com/prototypes/bakery-data`

Затем выбрать **Демо-команда Web Qadam** (`team-web`) и отправить:

- Идея: «Сделаем веб-интерфейс загрузки таблицы и просмотра рекомендаций по выпечке.»
- План: «Согласуем формат таблицы, реализуем загрузку и расчёт, покажем результат владельцу.»
- Срок: «Прототип через 10 дней после получения данных.»
- Ссылка: `https://example.com/prototypes/bakery-web`

URL — демонстрационные заглушки. Если на защите открываете прототип, заранее замените их реальными ссылками вашей команды.

### 4:15–4:50. Решение бизнеса

Вернуться к бизнесу и новой задаче, сравнить два предложения. Вручную принять Data Qadam, отклонить Web Qadam. Проверить статусы.

Реплика: «Команды сами выбирают задачи. Бизнес видит предложения и принимает решение самостоятельно; система никого не назначает».

Не начислять баллы команде просто за принятие предложения. Баллы за прогресс относятся к отдельному подтверждённому этапу и не обязательны для этого демо.

Оставшиеся 10 секунд — запас. Перед повторным прогоном сбросить демонстрационные данные поддерживаемым способом приложения; после появления бэкенда по контракту это `POST /api/demo/reset`. В полученном main этот эндпоинт ещё не реализован.
