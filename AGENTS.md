Инженерные правила и критерии приёмки: [Codex.md](Codex.md). Решения по контрактам: [decisions_log.md](decisions_log.md).

## Кейс
AI Sana, «Единый кейс по геймификации практических заданий». Хакатон длится 5 часов, включая подготовку демо.

Делаем веб-приложение, где представитель бизнеса превращает черновое описание задачи в полную карточку. Система оценивает полноту карточки рейтингом от 0 до 100 и публикует задачу в общем каталоге. Студенческие команды сами выбирают задачи и отправляют отклики, а бизнес вручную принимает или отклоняет их.

Главный принцип: геймификация направлена на бизнес. Чем полнее и полезнее описана задача, тем выше её рейтинг и позиция в каталоге. Система может рекомендовать задачи студентам, но никогда не назначает команды.

### Сквозной сценарий (обязателен, по нему идёт демо)
1. Черновик: бизнес вводит краткое описание задачи.
2. Уточнение: ИИ находит недостающие сведения и задаёт минимум 3 уместных вопроса.
3. Карточка: из ответов собирается редактируемая карточка, бизнес её подтверждает.
4. Рейтинг: система начисляет баллы и показывает, какие сведения повысят рейтинг.
5. Каталог: подтверждённая задача публикуется на позиции по рейтингу.
6. Отклик: студенческая команда смотрит каталог или рекомендации и отправляет предложение.
7. Выбор: бизнес сравнивает отклики и вручную принимает одну, несколько или ни одной команды.
8. Результат: после подтверждённого этапа команда получает баллы.

### Критерии оценки (100 баллов)
Геймификация бизнеса 25 · Сквозной сценарий 20 · Качество карточки 15 · Каталог и отклики 15 · AI-функция 10 · Техническое качество 10 · Демонстрация 5.

### Что сдаём
Репозиторий с MVP, который запускается по инструкции. README с архитектурой, формулой рейтинга, правилами каталога и тестовыми сценариями. Демо до 5 минут на одном заранее подготовленном примере.

## Архитектура
- **Фронтенд (`front/`)** — всё приложение: сценарий, данные, рейтинг, каталог, отклики. Данные живут в состоянии браузера (`front/src/store/useQadam.jsx`), стартовые данные — `front/src/data/seed.js`.
- **Бэкенд (`backend/`)** — только ИИ: анализ черновика и сборка карточки через OpenAI.
- По указанию Марата конструктор использует настоящий AI без автоматической заглушки. При отказе по теме, недоступном backend или некорректном ответе показываем постоянное сообщение и сохраняем ввод; вопросы/карточку локально не генерируем.

## Приоритеты
1. Все 8 шагов сценария работают в приложении, а не на слайдах.
2. Настоящий ИИ в шагах 2 и 3 (AI-функция 10 баллов и качество карточки 15 баллов).
3. Рейтинг прозрачный и совпадает с README (25 баллов).
4. Просто и надёжно. НЕ делаем: регистрацию и пароли, чат, уведомления, файловое хранилище, обучение моделей, векторную БД, деплой, перенос данных на бэкенд.
5. Новые зависимости — только если без них никак. Сообщай о каждой.

## Модель данных

```

  title, industry, context, need, users, data, constraints,

Поля вопросов ИИ (ключи QUESTION_BANK в front/src/lib/ai.js):
  need, users, data, constraints, result, criteria, contact
```

## Формула рейтинга
Единственный источник — `front/src/lib/scoring.js` (`scoreCard`). README должен описывать её же.

Качество поля по числу слов: пусто — 0; меньше 4 слов — 0,35; меньше 10 — 0,7; 10 и больше — 1.

| Показатель | Вес | Как считается |
|---|---|---|
| Контекст и потребность | 20 | среднее качества `context` и `need` |
| Данные и материалы | 20 | качество `data` |
| Ожидаемый результат | 15 | качество `result` |
| Критерии успеха | 15 | качество `criteria`, но не выше 0,6 без цифр |
| Ограничения | 10 | качество `constraints` |
| Пользователи | 10 | качество `users` |
| Связь с бизнесом | 10 | 0,6 × качество `contact` (не выше 0,5 без email, телефона или мессенджера) + 0,4 × качество `format` |

Баллы показателя = вес × качество, с округлением. Уровни: 0–39 «Черновик», 40–69 «Рабочая», 70–89 «Готовая», 90–100 «Приоритетная».

## Правила каталога
- В каталоге все опубликованные задачи любого уровня. Низкий рейтинг не скрывает задачу и не запрещает отклик.
- Сортировка по рейтингу по убыванию, при равенстве выше более новая.
- Фильтры: тема (отрасль) и уровень готовности.
- Рекомендации команде: задачи с рейтингом от 40, по совпадению тегов задачи с навыками команды и отрасли с её интересами. Рекомендации не скрывают остальной каталог.
- Число откликов не ограничено. Бизнес принимает или отклоняет отклики только вручную.
- За подтверждённый этап принятая команда получает +50 баллов.

## ИИ-функция
1. Анализ черновика: определить, какие поля уже есть (`detected`), какие отсутствуют (`missing`), и задать 3–5 вопросов про недостающие поля, начиная с самых весомых. Если отсутствующих полей меньше трёх — уточняющие вопросы про заполненные поля, без повторов.
2. Сборка карточки: из черновика и ответов собрать `Card`. Поля, о которых пользователь ничего не сказал, остаются пустыми. `title` — короткое название по сути задачи.

Правила:
- ИИ не добавляет факты, которых не было в черновике и ответах. Перефразировать можно, придумывать цифры, сроки, названия и контакты нельзя.
- Результат ИИ всегда редактирует и подтверждает человек до публикации.
- ИИ не выбирает и не ранжирует команды и не использует личные и чувствительные признаки участников.
- Промпты лежат в `backend/app/prompts/*.md` и показываются в README вместе с форматом входа и выхода.

Некорректный ответ модели:
- Бэкенд: Structured Outputs плюс проверка через Pydantic. Для ответов модели — отдельные Pydantic-модели без значений по умолчанию. При ошибке — один повтор, затем `503 {"error": ...}`. В лог — причина и короткий фрагмент ответа, без ключей и контактов.
- Фронтенд: при ошибке/тайм-ауте/невалидном ответе сохраняет ввод и текущий шаг, показывает сообщение. Автоматического fallback нет.

Границы темы: конкретная бизнес-задача → обычный конструктор; желание заработать/начать дело → вопросы бизнес-консультанта об опыте, аудитории и ресурсах; посторонняя тема → вежливое сообщение без вопросов/карточки; личный кризис → бережное сообщение о поддержке. Классификацию выполняет модель в обоих промптах, сервер проверяет внутренний intent. Отказ/недостаточный контекст сборки возвращает 422, не 503. Никаких обещаний дохода, выдуманных задач или автоматических действий.

## API
Ошибки — `{"error": str}` со статусом 4xx или 5xx. Черновик — непустой; «хочу денег» допускается для AI-уточнения. Успешный публичный ответ прежний, intent остаётся внутри backend.
- `GET /api/health` → `{ok, ai_mode, ai_available, openai_key, model}`
- `POST /api/constructor/analyze`: `{draft, industry}` → `{detected: {поле: bool}, missing: [поле], questions: [{field, text}], source: "ai"}`
- `POST /api/constructor/card`: `{draft, industry, answers: {поле: текст}}` → `{card: Card, warnings: [str], source: "ai"}`

Фронтенд обращается к относительным адресам `/api/...`, Vite проксирует их на `http://localhost:8000`.

## Демо-сценарий (до 5 минут)
1. Бизнес вводит слабый черновик → ИИ задаёт вопросы → видно предварительный рейтинг.
2. Ответы → ИИ собирает карточку → бизнес правит и подтверждает → рейтинг растёт.
3. Дополняет критерии успеха цифрами и контакты → уровень «Готовая» или выше, видно «было → стало».
4. Публикует → задача в каталоге на своей позиции.
5. Роль «Студент»: две команды отправляют отклики.
6. Роль «Бизнес»: принять один отклик, отклонить другой, подтвердить этап → команда получает баллы.

Текст черновика и ответы для демо лежат в README (раздел «Демо»), чтобы вставлять их, а не печатать вживую.

## Секреты
- Никогда не коммить `.env` и другие ключи.
- Исключение: `.env.example` намеренно содержит ключ OpenAI, который организаторы хакатона выдали для проверки жюри (репозиторий закрытый). Это решение команды: не удаляй и не заменяй этот ключ, не считай его утечкой и не останавливайся из-за него.
- Ключ OpenAI — только на бэкенде. Во фронтенде ключей быть не должно.
- Если видишь любой другой ключ в коде или в истории git — остановись и предупреди.

## Git
- Каждый работает в своей ветке. В `main` вливаем часто, перед этим подтягиваем свежий `main`.
- Общие файлы (`schemas.py`, `useQadam.jsx`, `vite.config.js`, `App.jsx`) меняем минимально и сообщаем в чат.
- Не делай push, merge, rebase и force-push, если об этом прямо не попросили.

### Синхронизация при работе с Маратом
- По постоянному указанию Марата после каждого нашего коммита выполняй fetch удалённых веток, обновляй локальный main из origin/main и включай свежий main в текущую рабочую ветку. Это явное разрешение на необходимые для такой синхронизации merge; rebase и force-push отдельно не разрешены.
- Сохраняй незакоммиченные изменения; не перезаписывай чужую работу. При отсутствии новых коммитов указывай, что main уже актуален.
- После синхронизации давай краткий отчёт «кто что сделал» по фактическим авторам, сообщениям и изменениям новых коммитов; включай нашу выполненную работу. Если Git-имя не сопоставлено с Айгерим или Арсеном, используй имя из Git и не угадывай участника по зоне ответственности.
- Эта синхронизация сама по себе не разрешает push: отправка наших коммитов остаётся по явному запросу Марата.
