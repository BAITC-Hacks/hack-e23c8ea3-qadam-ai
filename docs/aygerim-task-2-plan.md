# Вторая задача Айгерим: подключить ИИ к фронтенду

**Рабочая ветка:** `feat/ai-integration`.

**Основа плана:** `AGENTS.md`, `Codex.md`, контракт в `decisions_log.md` от 2026-09-23, состояние репозитория на `339461d`.

**Лимит каждой отдельной сессии:** до 400 000 токенов. Это верхняя граница контекста, а не цель расхода. Сессия заканчивается после выполнения её критерия приёмки; не нужно искусственно заполнять весь лимит.

## Цель и границы

Провести существующий конструктор через `POST /api/constructor/analyze` и `POST /api/constructor/card`: показать вопросы ИИ, получить редактируемую карточку и при сбое перейти на явно обозначенную локальную заглушку. Черновик и ответы пользователя должны сохраняться при ошибке. Публикация остаётся отдельным подтверждённым действием бизнеса, рейтинг продолжает считать код.

Файлы Айгерим по `AGENTS.md`: новый `front/src/lib/api.js`, `front/vite.config.js`, `front/src/store/useQadam.jsx`, `front/src/features/builder/Builder.jsx`, разделы README об интеграции. Для корректного разбора ответа понадобится точечная правка `front/src/lib/ai.js`; для честного отображения источника могут понадобиться `front/src/features/ai/AIModal.jsx` и строки `front/src/i18n/{ru,kk,en}.js`. Общие с Арсеном файлы менять минимально и заранее сообщить ему об этом в командном чате.

Роутер, сервис, промпты и тесты бэкенд-конструктора — зона Марата. Формула рейтинга, каталог, отклики и сохранение данных — вне этой задачи. Разногласие о JSON-хранилище и текущем `localStorage` уже отмечено в `decisions_log.md`; подключение ИИ его не решает.

### Итог этапа 0 — клиентский контракт для 1A–1C (2026-09-23)

Сверены `AGENTS.md`, `Codex.md`, `decisions_log.md`, текущие `backend/app/schemas.py`, `front/src/store/useQadam.jsx`, `front/src/lib/ai.js`, `Builder.jsx` и `AIModal.jsx`. Публичный API из `decisions_log.md` не меняется; отдельное согласование с Маратом для этого внутреннего контракта не требуется. Маршруты конструктора пока отсутствуют, поэтому приведённые ниже ответы — **моки для разработки**, а не результат живого ИИ.

**Клиент (`front/src/lib/api.js`).** Экспортировать `analyzeTask({ draft, industry }, { signal, timeoutMs } = {})` и `buildTaskCard({ draft, industry, answers }, { signal, timeoutMs } = {})`. Обе функции делают один `POST` JSON на относительные `/api/constructor/analyze` и `/api/constructor/card` соответственно и возвращают разобранный объект без изменения полей. Тайм-аут по умолчанию — **45 секунд**: на бэкенде возможны две попытки до 20 секунд каждая плюс небольшой запас на HTTP. Внешний `signal` нужен для отмены устаревшего запроса. Ошибки клиента имеют вид `ApiError` с `kind: 'http' | 'network' | 'timeout' | 'invalid-json' | 'aborted'`, `status` (число только для HTTP) и безопасным `message`. У `422` показывается `error` из JSON, если он строковый; отсутствие корректного тела ошибки заменяется общим сообщением. Ключ OpenAI и прямой вызов провайдера в клиенте отсутствуют.

**Ответы и проверка (`front/src/lib/ai.js`).** `validateAIResponse(payload, kind)` принимает уже разобранный объект или JSON-строку; `kind` — `'analyze'` либо `'card'`. Возвращает `{ ok: true, data: <проверенный объект> }` либо `{ ok: false, data: null }`, не создавая заглушку и не меняя состояние. Для ответа API требуется `source: 'ai'`. Неизвестные поля верхнего уровня и вложенных объектов отклоняются. Анализ содержит ровно семь известных ключей `detected` со значениями boolean; `missing` — массив уникальных известных полей, совпадающий с полями `detected === false`; `questions` — 3–5 объектов `{ field, text }` с уникальными известными `field` и непустым `text`. Для карточки обязательны все 11 строковых полей `Card`, `warnings` — массив непустых строк (допустим пустой массив). Проверка формы не доказывает истинность фактов: человек редактирует и подтверждает карточку.

**Локальный режим.** `analyzeDraft(draft)` возвращает тот же формат анализа с `source: 'stub'`; локальная сборка `buildLocalTaskCard({ draft, industry, answers })` возвращает `{ card, warnings: [], source: 'stub' }`. Вопросы заглушки могут иметь русский `text` для данных, а интерфейс показывает перевод из `ask_*`; вопросы ИИ показывает из `q.text`. Никаких дополнительных `refine` в потребительском ответе: уточнение уже выражено в `text`. Если ответ API содержит `source: 'stub'`, он не считается живым ответом: фронтенд сам создаёт локальную заглушку и явно обозначает её.

**Состояние конструктора.** После анализа `ai = { data, source, raw, card: null }`, где `data` — проверенный анализ, `source` — `'ai' | 'stub'`, `raw = JSON.stringify(data)` для совместимости с текущим `AIModal.jsx`. После сборки `ai.card = { source: 'ai' | 'stub', warnings: string[] }`; источник карточки может отличаться от источника вопросов. `AIModal` вправе читать `ai.raw`, но должен подписывать показанный промпт по источнику: локальный `AI_PROMPT` нельзя выдавать за промпт бэкенда. Баннер заглушки проверяет `source`, а не старый `ai.valid`. Предупреждения карточки видны до подтверждения; публикация остаётся отдельным действием.

**Переходы при ошибках.** `422` сохраняет черновик, отрасль, ответы и текущий шаг, показывает ошибку ввода, заглушку не запускает. Сеть, `503`, прочие HTTP-ошибки (включая текущий `404`), тайм-аут, не-JSON и невалидный ответ переводят соответствующую операцию в `stub`; уже введённые данные сохраняются. Отмена устаревшего запроса (`aborted`) не показывает ошибку и не запускает заглушку. На время каждой операции повторное нажатие заблокировано. У каждого запроса есть идентификатор/снимок входа: после изменения черновика, отрасли, ответов, сброса или повторного запуска запоздалый результат игнорируется. Ответы очищаются только после успешного **нового** анализа по действию пользователя, а не из-за сбоя или навигации назад.

**Одинаковые моки для 1B и тестов 1C.** Пример анализа:

```json
{
  "detected": { "need": false, "users": true, "data": false, "constraints": false, "result": true, "criteria": false, "contact": false },
  "missing": ["need", "data", "criteria", "constraints", "contact"],
  "questions": [
    { "field": "need", "text": "Что должно измениться для клиентов?" },
    { "field": "data", "text": "Какие данные доступны команде?" },
    { "field": "criteria", "text": "Как измерить успех решения?" }
  ],
  "source": "ai"
}
```

Пример карточки для черновика «Нужен бот для записи клиентов в салон» и ответа `need: "Автоматизировать запись клиентов"`:

```json
{
  "card": {
    "title": "Бот для записи клиентов", "industry": "Услуги",
    "context": "Нужен бот для записи клиентов в салон", "need": "Автоматизировать запись клиентов",
    "users": "Клиенты салона", "data": "", "constraints": "", "result": "Бот для записи клиентов",
    "criteria": "", "contact": "", "format": ""
  },
  "warnings": [], "source": "ai"
}
```

Для тестов 1C эти примеры — положительные случаи. Отрицательные: повреждённый JSON, отсутствующие/лишние ключи, не-boolean в `detected`, несогласованный `missing`, неизвестное поле, пустой или повторный вопрос, меньше 3 или больше 5 вопросов, нестроковое поле карточки, нестроковый `warnings`, ответ API с `source: 'stub'`. Мок 1B возвращает те же объекты; ошибки моделируются как описанные `ApiError`.

## Этап 3 — приёмка с настоящим ИИ (последовательно)

**Входной критерий:** задача 1 завершена, Марат реализовал оба маршрута, бэкенд и Vite запускаются локально. Ключ и модель настроены только на бэкенде; если ключа нет, проверить stub и явно записать, что живой режим не проверен.

1. Пройти пять подготовленных описаний: слабое, частично полное, подробное, противоречивое и с контактами. Убедиться, что вопросы уместны, минимум три, без выдуманных фактов; контактное поле не отправляется в модель, распознаваемые email/телефоны в свободном тексте маскируются на бэкенде.
2. Для каждого шага проверить цепочку `Vite → /api → FastAPI → UI`: источник `ai`, видимый текст вопросов, редактируемую карточку, предупреждения, ручное подтверждение и рейтинг из `scoring.js`.
